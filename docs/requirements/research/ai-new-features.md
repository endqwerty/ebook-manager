### What runs on the user's machine with open models (2026)
- Speech synthesis: Kokoro (82M parameters, Apache 2.0, 8 languages and 54 voices in v1.0; no speed figures on its model card). Verified: https://huggingface.co/hexgrad/Kokoro-82M. Third-party blog benchmarks give conflicting speeds (RTF 0.62 with 833 MB memory in one; "5x to teens" real-time on Apple silicon in others) and Piper real-time on a Raspberry Pi [unverified, blogs]. Piper's repository is reported GPL-3.0-or-later [unverified]; for an Apache project, run it as a separate process or avoid it. Rough need: about 0.3 GB of weights, a few hundred MB RAM, real-time or faster on a modern laptop CPU; on phones works via Core ML / ONNX, treat as "needs a per-device benchmark".
- Speech recognition and alignment: Whisper tiny 39M (~40 MB), base 74M (~76 MB), small 244M (~240 MB), 99 languages; browser WebGPU speeds of 2x to 15x real-time; Moonshine 6 to 61 MB, English only. Verified from one aggregator page: https://offlinetts.com/blog/tts-stt-landscape-h1-2026/ (no memory numbers; no licences stated). Aligning a 10-hour audiobook on a laptop is hours of CPU work, so it must be a resumable background job [inference].
- Embeddings: EmbeddingGemma, 308M parameters, 768 dimensions truncatable to 512, 256 or 128, 2,048 token window, 100+ languages, "under 200 MB RAM when quantized"; licence is the Gemma terms (not Apache). Verified: https://huggingface.co/blog/embeddinggemma. For a library of 5,000 books of about 100,000 words, with 300-token chunks, that is roughly 2 million chunks; at 256 dimensions as int8 about 0.5 GB [my arithmetic, not sourced].
- Small language models on phones: Gemma 3n E2B about 1.5 GB at 4-bit on a 6 GB phone; Llama 3.2 3B about 1.9 to 2.2 GB at Q4; newer Gemma 4 and Phi-4-mini reported as leaders in 2026. Search summary of blogs only [unverified]. A laptop with 16 GB runs 7 to 8B models; quality for long-book questions and recaps is unproven [inference].
- Summary: embeddings, TTS, STT and metadata tasks are feasible locally; whole-book chat and long-range recaps need a large context and are realistically optional cloud features or an opt-in local model.

## 2. Data the app must store
Beyond a first-round list:
- Derived text: per book and per format version, extracted plain text by chapter, with the content hash of the source file and the extractor version.
- Chunks: chunk id, book, chapter, start and end locator (EPUB CFI or character offset into the extracted text, and a fallback paragraph index), text hash, token count.
- Embeddings: vector (dimension, element type), model id, model version, truncation dimension, chunk hash it was built from; an index file that can be rebuilt.
- Summaries and recaps: scope (book, chapter, "up to position"), position covered (end locator), prompt id and version, model and provider, creation time, source text hash, spoiler boundary, and a flag for user-edited.
- Entities: type (person, place, term), canonical name, aliases, first-mention locator, occurrence list (locator, chunk), description with the position up to which it is spoiler-safe, extractor version.
- Consent: per book and per provider (local, named cloud service): allowed or not, what kinds of text may be sent (selection, chapter, whole book), set time, expiry.
- Egress log: time, book, provider, model, what range of text (locators and character count), purpose, result id; no text copy unless the user asks.
- Alignment: audio file id and hash, text version hash, ordered map of audio start and end times to text locators at sentence or word level, aligner and model version, confidence per segment, drift flag, manual corrections.
- Speech cache: voice id, model version, text hash, speed, audio file path, duration, size, last used, eviction priority.
- Translations: source language, target language, per paragraph or per locator side-by-side pairs, engine and version, with the source hash; kept apart from the original text.
- Handwriting and OCR: image or ink source id, recognised text, engine, language, per-word confidence, user corrections.
- Job records: type, target, status, resumable progress, error, resource limits, so heavy work (embedding, alignment, TTS) can pause and resume.
- Invalidation: a content hash of every file format variant, plus a "derived data stale" status; when a file is replaced, converted or its metadata edited, derived rows keep the hash they were built from and are marked stale or remapped, never silently reused. Annotations must be re-anchored with a text quote plus context so they survive a new edition. Kobo's 6.0 beta shows annotations and stats going missing after an update, so keep user data (highlights, stats) separate from rebuildable derived data and exportable.
- Annotation detail: highlights that touch or overlap must stay separate records with their own colour (Kindle regression of merged adjacent highlights).
- Reading statistics: sessions with start, end, locator range and device, not just a total; needed for Book Map, yearly summaries and reading goals.

## 3. Requirements a new manager should adopt that existing products get wrong
- Let authors, publishers and users see and control what leaves the machine: per-book, per-provider consent, with an egress log. Amazon's always-on, no opt-out design drew a formal Guild objection.
- Make every AI output show its model, version, position covered and date, and let the user delete or regenerate it; keep it outside the book file.
- Build spoiler safety on the reader's furthest position only: input text limited to what has been read, with the boundary stored beside the output. Amazon tightened Ask this Book only after complaints.
- Default to local or off; no cloud by default; no use of user notes for any training.
- Never let derived data overwrite or alter the user's file; keep alignments and translations sidecar.
- Label machine translations and narrations so they are not mistaken for human work (readers asked for transparency; Kindle Translate and Apple use labels).
- Check licences of bundled models: Piper is GPL, Gemma has its own terms, Kokoro is Apache. A model manifest with licence and size per model.
- Make user data survive firmware or app updates; export all annotations, stats and positions.

## Recommendation: plan data structures for now, build later
Plan now (cheap in the schema, costly to retrofit):
1. Content hash and format-variant identity for every file, with a stale flag for anything derived.
2. A stable locator model (CFI plus text-quote anchor plus offset) used by annotations, chunks, summaries, entities and alignment.
3. Extracted text per chapter and a chunk table keyed by locator.
4. A generic "derived artifact" table: kind, source hash, producer (model, version, provider), scope, position covered, created, status, so summaries, embeddings, entity lists, translations, speech and alignments share one invalidation rule.
5. Consent and egress-log tables, per book and per provider, even if the first release has no cloud features.
6. Reading sessions (not only totals) and separate, never-merged highlight records.
7. Job queue with resumable progress.
8. Sidecar storage for large blobs (vectors, audio, alignment) outside the main database, rebuildable.
Defer building: chat with a book, recaps, entity extraction, alignment, neural TTS, cover generation. Of these, local embeddings for library search and local TTS are the most feasible first; Whisper-based alignment second.
