# macOS app

For [the macOS app](https://github.com/endqwerty/ebook-manager/issues/141).
[Platforms](platforms.md) chose the parts: a SwiftUI shell, the shared Rust
core through UniFFI, and WKWebView for EPUB layout. This page says how those
parts are built and joined, and how the reader's helper is isolated on a Mac.

## Problem

The app runs only on Linux. The reader's helper is isolated with bubblewrap,
which macOS doesn't have. The device export reaches its folder through `/proc`.
The only shell is GTK. A reader with a Mac can't use any of it.

## Goals

- The first release path of the [desktop walk-through](desktop-mvp.md) works on
  macOS 14 or later, on Apple silicon and Intel: import EPUBs, find and correct
  them, read with the place kept, export to a mounted folder.
- No book byte is parsed in the app's process, and the helper that parses
  refuses to run unconfined (SEC-1 to SEC-10 in
  [constraints](../requirements/10-constraints.md#opening-untrusted-files)).
- One command builds and tests the app from a terminal and in CI.

## Non-goals

- Signing with a Developer ID, notarisation, a DMG and updates. The build signs
  ad hoc so the app runs on the machine that built it.
- The Mac App Store. Its sandbox forbids the isolation used here; see
  [the helper](#the-helper-on-macos).
- MOBI conversion (`ebook-convert`) on macOS, the shelf view, the table view
  and reader settings beyond what the first walk-through needs. Each follows
  in its own change.

## Plan

```
apps/macos (SwiftUI, AppKit where needed)
   │  Swift calls, generated by UniFFI
crates/ebook-bridge (Rust, staticlib)      one object per library, plain records
   │
ebook-library   ebook-reader ──▶ ebook-reader-helper under sandbox-exec
ebook-device
```

### The bridge

`crates/ebook-bridge` is the one crate Swift links. It holds no rules of its
own beyond joining the core crates: staging a file, asking the helper for its
metadata and handing both to the library is one call, as it is one step for a
user. It exposes:

- `Library`: open at a directory; import files with a result for each and a
  second call to settle a review; browse by query and sort order as a count
  and windows of rows; a book's full record and edits to it; covers as PNG
  bytes; the managed file's export to a folder.
- `OpenBook`: chapters, contents, a chapter's markup, a picture's bytes, and
  the saved place.

Every call blocks. Swift calls them from a background executor and never from
the main actor. Errors cross as one enum whose message can be shown as it is.
Records carry no file path of the library's, except the export's destination.

The GTK shell has the same joins in `apps/desktop/src` (`imports.rs`,
`thumbs.rs`, `browse/`). The bridge writes them against the core crates
without moving the GTK code. Once both shells work, the GTK shell should call
the bridge's Rust API and its copies go.

A decision that would be wrong if: Swift needs to hold a view of a hundred
thousand rows and each window costs more than a frame through UniFFI's
serialisation. Measure a 128-row window at 100,000 books; above 4 ms, move
the row list to a C buffer.

### The shell

`apps/macos` is a Swift package with no Xcode project. `apps/macos/build.sh`
builds the Rust static library and the helper, generates the Swift binding,
runs `swift build`, and assembles `Ebook Manager.app` with the helper beside
the main program in `Contents/MacOS`, which is where
[helper discovery](../../crates/ebook-reader/README.md#helper-discovery) looks.
A package builds on a Mac with only the command-line tools and on a CI runner.

The library lives in `~/Library/Application Support/Ebook Manager`. The window
is a `NavigationSplitView`-free single column for now: toolbar with search,
view switch (grid, list) and sort; the grid is an AppKit collection view once
SwiftUI's lazy grid falls short at 100,000 books. The
[interface design](interface.md) governs what is drawn.

The reader is a WKWebView with book scripts blocked by Content Security Policy
(`default-src 'none'`, because `WKWebpagePreferences.allowsContentJavaScript =
false` also disables `WKUserScript` in isolated `WKContentWorld`s). A
`WKURLSchemeHandler` on a scheme of its own serves a chapter's markup wrapped
in the app's document as `application/xhtml+xml`, `/s/reader.css`, and pictures
by id. The reader's own script and style come from
[`apps/desktop/src/reader`](../../apps/desktop/src/reader/README.md), shared,
not copied. No other request leaves the view: a content rule list blocks every
URL outside the scheme.

### The helper on macOS

The helper is the same program. The host starts it through
`/usr/bin/sandbox-exec` with a fixed profile that denies everything and then
allows: running and reading the helper, reading the one book, and reading the
system's own libraries. The helper and book paths are profile parameters, so
no path is spliced into the profile's text. The host resolves both paths
first, because the profile matches resolved paths.

What bubblewrap gave on Linux, and what gives it here:

| Linux | macOS |
|---|---|
| Mount namespace showing only the helper, the book and libraries | Profile denies every file but those |
| Network namespace | Profile denies all network use |
| No new processes: process limit of one | Profile denies fork; the process limit is set as well |
| Address-space limit | macOS refuses an address-space limit below what a process already maps. The helper's allocator counts what it hands out and refuses beyond `Limits::memory_bytes`, which ends the helper as running out of memory does on Linux |
| Dies with the application: parent-death signal | The helper exits when its input closes, and its CPU limit ends a call in progress |
| Every descriptor above stderr closed on exec, by `close_range` | The same, set one by one up to the highest descriptor the application has open |

The helper keeps checking for itself before it reads a book: that it can read
nothing about `/Users`, `/etc`, `/tmp`, `/var`, `/Library` and their like, that
it can't write, has no network and can't start a process. Outside the profile
each of those fails, so there is no unconfined run. The checks are a tripwire
for a missing profile. What the profile itself allows is checked by a test
that runs a probe under it.

`sandbox-exec` is marked deprecated in its manual page. It is what the system's
own build and browser sandboxes are driven by, and nothing else gives a
deny-by-default child without a signing identity. If Apple removes it,
`Reader::new` reports that the sandbox is unavailable and no book opens: the
app fails closed. The replacement would be an App Sandbox XPC service, which
needs the signing work this page defers. An app under the App Sandbox can't
apply a second profile, which is why the Store is a non-goal.

A decision that would be wrong if: a book can make the helper read a file
other than itself, reach the network or leave a process behind. The tests in
`crates/ebook-reader/tests` run on macOS and include a helper started without
the profile, which must refuse.

### Device export

`ebook-device` named files through `/proc/self/fd`, which macOS lacks. It now
opens, creates and renames every file relative to the open directory's
descriptor (`openat`, `renameat` without replacing) on both systems, so there
is one implementation and no path to go stale.

## Behaviour

1. When the helper is started without the profile, it replies that it isn't
   isolated and reads nothing. `tests/failures.rs`.
2. When a book is opened, the helper can't read another file, write, reach the
   network or start a process. The helper's own check, run at every start.
3. When the helper needs more memory than its limit, the call fails with an
   error and no crash report appears. `tests/failures.rs`.
4. When a folder with a book, its duplicate, a revised copy and a broken file
   is imported, each gets its own result and the window shows one book until
   the revision is settled. Bridge tests, on Linux and macOS.
5. When the app is closed and opened again, the book opens at the place it was
   left. Bridge tests for the stored place; the app's UI test for the view.
6. When a book is sent to a folder twice, the second send reports that it is
   already there. `crates/ebook-device/tests`.

## Alternatives

- **An Xcode project.** Needs Xcode's first-run setup on every machine and a
  project file agents can't review as text. Turned down for the package; a
  generated project can come back if a capability needs one.
- **The helper as an App Sandbox XPC service.** The right shape for a signed
  release, and coarser: the App Sandbox lets a process read most of the
  system. It needs a signing identity and a bundle for every test run.
- **The helper sandboxing itself with `sandbox_init`.** Its documented form
  takes only named profiles, none of which denies file reads. The form that
  takes a profile's text is private.
- **Passing the book as an open descriptor**, so the profile names no file.
  Tighter by one rule, and it needs unsafe code in the helper to adopt the
  descriptor. Worth doing with the XPC service.
